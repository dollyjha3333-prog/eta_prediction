# ETA Prediction for Last-Mile Delivery

An **end-to-end machine-learning project** that predicts Estimated Time of Arrival (ETA) for
last-mile delivery trips. It goes from raw trip data all the way to a production-minded model,
with every number in this README produced by actually executing `notebooks/eta_prediction.ipynb`
(nothing is hand-typed — see `results/metrics.json`).

---

## 1. Problem framing — why ETA prediction matters

ETA is operational infrastructure, not a nice-to-have:

- **Customer trust** — the delivery window is a promise; every minute of miss drives "where is my order?" tickets.
- **Dispatch planning** — dispatchers sequence stops using expected travel times; systematic ETA bias cascades into missed windows.
- **SLA compliance** — contracts carry SLAs ("90% of orders within 45 min"); MAE/RMSE map directly to breach risk.
- **Driver / fleet allocation** — capacity planning ("how many vans for the lunch peak?") depends on expected trip duration.

The hard part: travel time is **non-linear and contextual**. The same 10 km takes far longer at
08:30 on a rainy weekday than at 03:00 on a clear Sunday. A naive `distance / average_speed` estimate
cannot capture this — which is exactly why we train models and compare them to that baseline.

---

## 2. Dataset

We use a **synthetic but realistic** dataset generated by `src/generate_dataset.py` (deterministic, seeded,
20,000 trips). Synthetic data keeps the repo fully reproducible with no external download, and lets us
*know* the true generative process so we can prove a model recovers signal a baseline misses.

The target is built from a known physical-ish rule:

```
travel_time = distance / effective_speed * 60 + stops*0.7 + turns*0.15 + noise
effective_speed = vehicle_speed * traffic_factor * weather_factor * (1 - 0.3*congestion)
```

| Field | Meaning |
|---|---|
| `timestamp` | trip start (spread across 120 days) |
| `pickup_lat/lon`, `drop_lat/lon` | geo coordinates |
| `distance_km` | haversine distance |
| `vehicle_type` | bike / car / van |
| `weather` | clear / cloudy / rain / snow / fog (season-dependent) |
| `hour`, `day_of_week`, `is_weekend`, `is_holiday`, `time_bucket` | calendar features |
| `num_turns`, `num_stops`, `route_complexity` | route structure |
| `historical_avg_speed` | area's typical speed (ignores live traffic) |
| `area_congestion_index` | 0..1 zone congestion |
| `actual_eta_min` | **target** (true travel time, minutes) |

*(A real project would swap this for NYC/Chicago rideshare data or a Kaggle logistics dataset and feed a
live traffic API instead of the `area_congestion_index` proxy.)*

---

## 3. Feature engineering

Four families, each justified by the signal it carries:

**Time-based** — `hour`, `day_of_week`, `is_weekend`, `is_holiday`; cyclic `hour_sin/hour_cos`,
`dow_sin/dow_cos` (so 23:00 and 00:00 are adjacent, not opposite); `time_bucket` (rush / midday / offpeak)
as a coarse peak-demand proxy.

**Distance / route-based** — `distance_km` (dominant driver), `num_turns` & `num_stops` (dwell/slow-down),
`route_complexity` (turns per km isolates twisty urban routes).

**Historical / aggregate** — `historical_avg_speed` (strong prior that *doesn't* know live traffic, so it
leaves signal for the model) and `area_congestion_index` (zone load).

**External** — `weather` and `vehicle_type` (different base speeds / weather penalties), one-hot encoded.

---

## 4. Train / test split — time-based

We split **chronologically** (first 80% train, most recent 20% test):

- **Train:** 2025-01-01 00:00:09 → 2025-04-06 05:46:37 (16,000 trips)
- **Test:**  2025-04-06 05:48:16 → 2025-04-30 23:56:01 (4,000 trips)

A **random** split would leak future information: consecutive trips share the same traffic/weather/congestion,
and a model would "memorise the immediate past" and report optimistically biased accuracy that won't hold in
production. Time-based split is the honest evaluation that matches real deployment (predict the future from the past).

## 5. Model selection & results

We compare four estimators. **All metrics are on the held-out time-based test set (minutes, except MAPE).**

| Model | MAE | RMSE | MAPE | % within ±5 min |
|---|---:|---:|---:|---:|
| Baseline (dist / hist speed) | 47.69 | 71.54 | 41.49% | 6.25% |
| Linear Regression | 17.37 | 26.37 | 32.91% | 24.73% |
| Random Forest | 3.65 | 6.24 | 5.14% | 78.08% |
| **LightGBM (best)** | **2.63** | **3.76** | **4.01%** | **87.83%** |

**Reading the table**

- The **baseline** is terrible (MAE ~48 min, only 6% within ±5) because it ignores live traffic/weather.
- **Linear Regression** already helps (MAE 17.4) but can't model interactions like *rush-hour × rain*.
- **Random Forest** is a big jump (MAE 3.65, 78% within ±5).
- **LightGBM** wins on every metric (MAE 2.63, RMSE 3.76, 87.8% within ±5), i.e. **94.5% lower MAE than the baseline**
  and ~24% lower MAE than Random Forest.

**Trade-off:** LightGBM gives the best accuracy but is the least interpretable and needs tuning/retraining
discipline. Linear Regression is the interpretable benchmark. In production you'd often ship LightGBM and keep
Linear/RF as explainability and fallback references.

## 6. Metrics, explained

- **MAE** — average absolute error; the most business-interpretable ("our ETAs are off by ~X min").
- **RMSE** — penalises large errors; a single 60-min blowout hurts more than many 1-min errors.
- **MAPE** — percentage error, so short and long trips are compared fairly.
- **% within ±5 min** — practical SLA-style KPI ("how often are we close enough?").

## 7. Real-world use & implementation

**Serving modes**
- *Batch* — periodic scoring of known routes for planning/capacity.
- *Real-time API* — a `/eta?pickup=…&drop=…&vehicle=…` endpoint at dispatch; LightGBM scores in <1 ms.

**For production**
- Replace `area_congestion_index` with a **live traffic API** (Google/TomTom/HERE) at request time.
- **Retraining cadence** (weekly/monthly) to counter seasonal drift and new zones; monitor feature distributions.
- **Fallback** for cold-start routes with no history: degrade to the distance/historical-speed baseline and flag `low_confidence=True`.

**Monitoring / degradation detection**
- Log every `(predicted, actual)` as deliveries complete; track **rolling 7-day MAE**.
- Alert when MAE crosses a threshold (e.g. baseline×1.2 or a fixed business limit); dashboard `% within ±5 min` as the headline SLA KPI.
- Drift alarms on input features (weather shifts, new vehicle types) trigger retrain.

---

## 8. Limitations & next steps

- **Synthetic data** — clean generative rule; real travel time has fatter tails and driver-behaviour variance we don't model.
- **No live traffic / no road-network distance** — haversine + a daily congestion proxy; a routing engine (OSRM/Valhalla) + live feed is the biggest real accuracy lever.
- **Unpredictable events** — accidents, closures, festivals are absent.
- **Driver behaviour** — individual speed/route/break choices are aggregated away.

**Next:** live traffic + routing API, driver-level features, quantile/conformal prediction for reliable ETA *intervals*, and the monitoring loop above.
